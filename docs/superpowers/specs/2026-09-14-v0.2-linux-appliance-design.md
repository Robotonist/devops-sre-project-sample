# Ops Appliance v0.2 Linux Appliance Design

Date: 2026-09-14
Status: Approved design; ready for implementation planning

## Purpose

v0.2 moves the Ops Appliance from a Docker Compose development environment into a production-style single-node Linux appliance deployment.

The goal is not to redesign the monitoring application. v0.1 already established the application boundaries: FastAPI for management and history, PostgreSQL for durable state, Redis for transient queueing, Celery Worker for probe execution, and Celery Beat for recurring scheduling. v0.2 preserves those boundaries and replaces the local Compose deployment model with a reproducible Linux host, rootless Podman containers, systemd/Quadlet supervision, Ansible configuration management, and versioned multi-architecture release images from GitHub Container Registry.

The core outcome is a fresh Ubuntu VM that can be converted into the appliance through Ansible, rebooted, and return to a healthy state automatically with PostgreSQL data preserved and recurring monitoring resumed.

## Scope

v0.2 includes:

- Ubuntu 26.04 LTS ARM64 as the initial appliance host in UTM on Apple Silicon
- UTM Shared Network mode for the development appliance
- Ansible-owned host configuration after the base Ubuntu install and first SSH access
- a dedicated `opsappliance` Linux service account
- rootless Podman for all appliance workloads
- administrator-managed user-scoped Quadlet definitions
- systemd user services with lingering enabled for boot-time startup
- independent Quadlet units for API, Worker, Beat, PostgreSQL, and Redis
- a private Podman network shared by those services
- API-only host exposure on TCP/8000
- host firewall rules allowing SSH and the API while denying unnecessary inbound access
- persistent PostgreSQL storage
- intentionally ephemeral Redis state
- deployment-time Alembic migrations
- public GitHub Container Registry release images
- multi-architecture images for `linux/arm64` and `linux/amd64`
- explicit versioned image deployment rather than `latest`
- CI validation for application checks, Ansible assets, and release image builds
- repeatable/idempotent Ansible deployment
- reboot recovery as a hard release criterion

## Non-goals

The following remain intentionally out of scope for v0.2:

- production TLS termination
- reverse proxy deployment
- authentication or authorization
- private registry credentials
- enterprise secret-management integration
- Ansible Vault as a required secret-management mechanism
- image digest pinning
- image signing or signature verification
- SBOM generation or attestations
- centralized metrics, logs, traces, or dashboards
- production alert delivery
- automated rollback
- backup/restore workflows
- high availability
- multi-node orchestration
- Kubernetes
- automated creation of the UTM VM itself
- AWS infrastructure provisioning

These concerns are deferred to later project milestones so v0.2 can stay focused on Linux appliance deployment and lifecycle supervision.

## Design principles

v0.2 follows these principles:

1. **Preserve application failure boundaries.** API, Worker, Beat, PostgreSQL, and Redis remain independently managed processes.
2. **Separate host administration from workload execution.** Ansible may use elevated privileges to configure the appliance, but the application workload runs without root privileges.
3. **Build once, deploy the same artifact.** CI produces release images; the appliance never builds application source code.
4. **Keep durable and transient state distinct.** PostgreSQL survives restart and reboot; Redis may be recreated empty.
5. **Expose only what clients need.** The API is reachable from the host network; PostgreSQL and Redis are not.
6. **Make desired state repeatable.** Ansible runs should be idempotent and converge the host toward the same configuration.
7. **Use systemd for lifecycle, health checks for usability.** Service ordering does not replace readiness validation.
8. **Avoid infrastructure complexity without a requirement.** v0.2 remains a single-node appliance and does not introduce Kubernetes or cloud infrastructure.

## Approaches considered

### Host deployment model

Three broad approaches were considered:

1. Docker Compose on Linux
2. rootful Podman/systemd
3. rootless Podman with systemd/Quadlet

Docker Compose would have required the smallest change from v0.1 but would not add enough new operational depth. Rootful Podman would simplify systemd integration but weaken the least-privilege story. Rootless Podman with Quadlet was selected because it preserves containerized service boundaries while introducing realistic Linux supervision and a meaningful host/workload privilege boundary.

### VM platform

UTM was selected over Multipass and VMware Fusion. Multipass is convenient but intentionally abstracts more of the VM lifecycle. VMware Fusion adds another vendor layer. UTM exposes VM, storage, networking, and guest installation details clearly enough to make the appliance host itself part of the learning experience.

### Registry model

Public GHCR images were selected over private images or manual image transfer. The repository is public, so requiring registry credentials would add secret-distribution work before the project needs it. A public release artifact keeps deployment deterministic without putting GitHub credentials on the appliance.

## Host platform

The initial v0.2 appliance runs as an ARM64 Ubuntu 26.04 LTS VM in UTM on an Apple M1 Max host.

UTM Shared Network mode is used initially. This gives the Mac host connectivity to the guest without adding bridged-network complexity during the first Linux deployment milestone. Bridged networking can be explored later as a separate exercise if appliance-on-LAN behavior becomes useful to demonstrate.

The UTM VM itself is created and Ubuntu is installed manually. Automation begins once the VM is booted and reachable through SSH.

This manual bootstrap boundary is intentional: v0.2 automates the Linux appliance, not the desktop hypervisor.

## Host and privilege ownership

An administrative deployment user exists on the Ubuntu VM and is reachable over SSH. Ansible connects using that account and uses privilege escalation only for tasks that require host-level changes.

Ansible creates a dedicated service account:

```text
opsappliance
```

The `opsappliance` account:

- runs Podman rootlessly
- owns application runtime state
- owns or is granted appropriate access to persistent container storage
- does not need interactive login for the appliance to operate
- does not receive general administrative privileges

Ansible configures the prerequisites required for rootless containers, including subordinate UID/GID mappings where required by the host distribution.

### Administrator-managed user Quadlets

Quadlet definitions are installed under the administrator-controlled user-scoped path:

```text
/etc/containers/systemd/users/<opsappliance-uid>/
```

This means root/Ansible owns the deployment definitions, while the generated services execute inside the `opsappliance` user manager and run rootless Podman.

This is preferred over storing deployment definitions in the service account's home directory because the service account should not implicitly own the authoritative deployment configuration.

### Boot-time rootless services

Ansible enables lingering for `opsappliance` so its systemd user manager is created during boot and can continue running without an interactive login session.

Quadlet units include an install relationship equivalent to:

```ini
[Install]
WantedBy=default.target
```

The result is that a reboot does not require a user login or manual `podman start` commands.

## Runtime topology

All appliance services remain separate containers on one private Podman network.

```text
Ubuntu 26.04 VM
|
+-- host firewall
|   +-- SSH allowed
|   +-- TCP/8000 allowed
|
+-- opsappliance systemd user manager
    |
    +-- private Podman network
        |
        +-- API
        +-- Worker
        +-- Beat
        +-- PostgreSQL
        +-- Redis
```

Each service has its own Quadlet definition and generated systemd service. They are not collapsed into a single Podman pod.

This preserves the v0.1 failure model:

- Worker can restart without restarting API or PostgreSQL
- Beat can fail independently of Worker
- API can fail without deleting state
- PostgreSQL and Redis remain separate dependencies

## Networking and firewall

The appliance uses a private Podman network for service-to-service communication.

Expected internal relationships include:

```text
API ------> PostgreSQL
API ------> Redis
Beat -----> PostgreSQL
Beat -----> Redis
Worker ---> PostgreSQL
Worker ---> Redis
Worker ---> monitored targets
```

Only the API publishes a host port. PostgreSQL and Redis do not publish host ports.

For v0.2 the API is exposed as plain HTTP on TCP/8000. TLS termination and a reverse proxy are deferred.

The host firewall follows a default-deny inbound posture with explicit allowances for:

- SSH administration
- API TCP/8000

The exact firewall mechanism will be selected during implementation planning based on Ubuntu 26.04 defaults and package availability, but the behavioral requirement is fixed: only required inbound services are permitted.

## State and durability

### PostgreSQL

PostgreSQL remains the durable source of truth for:

- target definitions
- target enable/disable state
- monitoring intervals
- expected status codes
- TLS warning thresholds
- optional version endpoint configuration
- historical check results

PostgreSQL receives persistent Podman-managed storage. Recreating or restarting the PostgreSQL container must not erase the database.

The v0.2 reboot acceptance test explicitly verifies that target configuration and historical results still exist after a full Ubuntu reboot.

### Redis

Redis remains transient queue infrastructure.

Redis does not require durable persistence in v0.2. A reboot may discard queued work. Once Redis, Beat, and Worker return, recurring checks should resume from the durable target definitions in PostgreSQL.

This remains an accepted recovery boundary:

```text
Redis loss -> transient queued work may be lost
PostgreSQL loss -> durable application state is lost
```

## Container images and release artifacts

The Ubuntu appliance does not clone the application repository and does not build the runtime image.

GitHub Actions owns application artifact creation.

The release flow is:

```text
Git repository
    |
    v
GitHub Actions
    |
    +-- tests/lint
    +-- runtime build
    +-- multi-architecture build
    v
GitHub Container Registry
    |
    v
Ansible-selected release version
    |
    v
Podman pull on appliance
```

### Multi-architecture images

Release images support:

- `linux/arm64`
- `linux/amd64`

This allows the same release tag to deploy to the local ARM64 UTM appliance and to future AMD64 Linux hosts without maintaining architecture-specific deployment configuration.

### Version policy

The appliance configuration deploys an explicit release version, for example:

```yaml
ops_appliance_version: "v0.2.0"
```

The deployment configuration must not use `latest`.

For v0.2, release tags are the deployment interface. Digest pinning is deferred to the secure-delivery/lifecycle milestones.

## PostgreSQL and Redis images

PostgreSQL and Redis remain containerized rather than installed as Ubuntu packages. This keeps the application stack under one container lifecycle model and avoids mixing host-package application dependencies with Quadlet-managed services.

Their versions must be explicit rather than floating tags. The implementation plan will retain or deliberately update the versions already proven in v0.1, subject to architecture support and compatibility testing.

## Migrations and startup

Database schema migration is a deployment concern, not an ordinary boot concern.

A new deployment follows this sequence:

```text
render/install configuration
    |
pull requested images
    |
ensure PostgreSQL running and accepting connections
    |
run one-shot Alembic migration
    |
start/restart API, Worker, and Beat
    |
wait for application readiness
```

A normal VM reboot follows a different path:

```text
Ubuntu boot
    |
systemd user manager starts
    |
Quadlet services start
    |
existing PostgreSQL state is reused
    |
API/Worker/Beat reconnect
    |
monitoring resumes
```

Migrations are therefore not intentionally rerun as a boot-time side effect.

## Service dependencies and health

systemd relationships express lifecycle requirements, but process state is not treated as proof of dependency readiness.

For example, PostgreSQL being `active` does not guarantee that it is ready to accept connections.

The implementation will preserve real health checks and API readiness semantics.

The division of responsibility is:

```text
systemd / Quadlet -> lifecycle and ordering
health checks       -> dependency usability
/readyz             -> application usefulness
```

A deployment is not considered successful until the API readiness check succeeds.

## Ansible ownership

After initial Ubuntu installation and SSH access, Ansible owns the desired appliance host configuration.

The proposed repository structure is:

```text
ansible/
|-- inventory/
|   `-- local.ini
|-- group_vars/
|   `-- all.yml
|-- roles/
|   |-- base/
|   |-- podman/
|   |-- appliance/
|   `-- firewall/
`-- deploy.yml
```

### `base` role

Responsible for:

- baseline required packages
- `opsappliance` service account
- required directories and ownership
- systemd lingering
- small host prerequisites required by later roles

### `podman` role

Responsible for:

- Podman installation
- rootless Podman prerequisites
- subordinate UID/GID configuration where required
- Podman/network prerequisites needed by the appliance

### `appliance` role

Responsible for:

- Quadlet network definitions
- Quadlet volume definitions
- Quadlet container definitions
- safe application configuration files
- local secret/environment file placement
- explicit release image version
- pulling required application images
- systemd user daemon reload
- PostgreSQL availability
- one-shot migration execution during deployment
- application service start/restart
- readiness verification

### `firewall` role

Responsible for:

- default-deny inbound behavior
- SSH allowance
- API TCP/8000 allowance
- preventing accidental external exposure of data services

## Idempotence

Running the deployment playbook repeatedly against an already-correct host should not create duplicate users, duplicate rules, duplicate storage, or unnecessary configuration divergence.

A second Ansible run is part of the v0.2 acceptance test.

The second run does not need to report every task as unchanged if a task genuinely performs a safe verification action, but it must leave the host in the same desired state and must not break the running appliance.

## Configuration and secrets

Safe deployment configuration may be committed as normal Ansible variables. Examples include:

- application image name
- application version
- published API port
- service-account name
- paths
- non-sensitive runtime settings

Real secrets must not be committed.

For v0.2, secrets use a deliberately simple boundary:

- a local vars file or environment input ignored by Git
- a committed example file documents required secret keys
- Ansible renders or installs required runtime secret material with restrictive permissions

Ansible Vault or a dedicated secret-management platform is not required for v0.2. Stronger secret handling remains a later milestone.

## CI and validation

Existing v0.1 validation remains in place:

- application tests
- Ruff linting
- runtime container build
- Compose integration environment
- migrations
- `/readyz`
- deterministic vertical-slice smoke test

v0.2 adds validation for deployment assets. At minimum, CI should cover:

- Ansible/YAML syntax validation
- `ansible-lint`
- rendering or static validation of deployment templates where practical
- multi-architecture application image build capability

Actual UTM VM boot testing is not required inside GitHub Actions. The Linux-appliance acceptance test runs against the controlled Ubuntu VM.

## Release behavior

Normal pull requests and pushes continue to validate the repository.

Release publishing is separate from ordinary validation. A version release such as `v0.2.0` triggers or participates in creation of the public GHCR multi-architecture runtime image.

The deployed appliance references the chosen release version explicitly.

The production host is therefore a deployment consumer, not a build worker.

## Failure behavior

The Linux deployment must preserve the v0.1 failure boundaries.

Expected behavior includes:

| Failure | Expected v0.2 impact |
| --- | --- |
| Worker stopped | API remains reachable; probes stop executing |
| Beat stopped | API/Worker remain available; recurring dispatch stops |
| Redis stopped/recreated | queued work may be lost; durable database state remains |
| PostgreSQL unavailable | API readiness fails; durable operations unavailable |
| monitored target unavailable | failed check is recorded; Worker stays alive |
| VM reboot | services return automatically; PostgreSQL state remains; checks resume |

At least one process-isolation failure test is required before release. The preferred initial case is stopping the Worker and confirming that the API remains reachable.

## Deployment failure behavior

Ansible should fail loudly when deployment cannot produce a usable appliance.

The final deployment phase waits for `/readyz` with a bounded retry period. If readiness never succeeds, the playbook fails rather than reporting a successful deployment.

The implementation should make systemd/Podman status and logs easy to inspect after such a failure.

Automated rollback is not required in v0.2.

## Operator workflow

The intended v0.2 high-level operator flow is:

```text
1. Create Ubuntu 26.04 ARM64 VM in UTM
2. Complete base install and SSH setup
3. Configure Ansible inventory/secret inputs locally
4. Run Ansible deployment
5. Verify readiness
6. Create monitoring target
7. Verify recurring checks
8. Re-run Ansible
9. Reboot VM
10. Verify automatic recovery and durable state
```

Exact commands will be defined in the implementation plan and README updates.

## Acceptance criteria

v0.2 is complete only when all of the following are demonstrated:

1. A fresh Ubuntu 26.04 ARM64 VM is reachable over SSH.
2. One documented Ansible deployment configures the required host state and deploys the appliance.
3. Application services run as the dedicated `opsappliance` user through rootless Podman.
4. API, Worker, Beat, PostgreSQL, and Redis exist as independent Quadlet/systemd-managed services.
5. PostgreSQL and Redis are reachable only through the private appliance container network, not through published host ports.
6. The host firewall allows required administration and API traffic while denying unnecessary inbound services.
7. The API becomes healthy and ready after deployment.
8. A monitoring target can be created and recurring results are persisted.
9. Re-running the same Ansible deployment succeeds without breaking or duplicating the installation.
10. Stopping the Worker does not stop the API.
11. A full Ubuntu reboot requires no manual container startup.
12. The monitoring target and historical PostgreSQL data survive the reboot.
13. New recurring checks resume after reboot.
14. CI validates the Ansible assets and the existing application test/smoke path.
15. CI can produce the release application image for both ARM64 and AMD64.
16. The appliance deploys an explicit versioned GHCR image and does not use `latest`.

## Architecture progression

v0.1 proved the application-level boundaries using Docker Compose.

v0.2 proves that the same application can be delivered as a supervised single-node Linux appliance without redesigning the application itself.

Later milestones can layer additional production concerns onto this base:

```text
v0.1  application + Compose boundaries
  |
v0.2  Linux appliance + Podman + systemd + Ansible
  |
v0.3  observability
  |
v0.4  reliability operations
  |
v0.5  secure software delivery
  |
v0.6  backup / upgrade / rollback lifecycle
  |
v1.0  polished reproducible appliance
```

Kubernetes remains intentionally deferred. If future requirements introduce multi-node scheduling, high availability, or horizontal orchestration, Kubernetes can be evaluated as a deployment evolution rather than as a prerequisite for the current appliance model.
