# Ops Appliance v0.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the first runnable local release of the Ops Appliance: FastAPI + PostgreSQL + Redis + Celery Worker + Celery Beat, with HTTP/TLS/version probes, durable results, Docker Compose, tests, and CI.

**Architecture:** FastAPI owns configuration and query APIs; PostgreSQL is the durable source of truth; Redis is transient queue infrastructure; Celery Worker executes probes; Celery Beat triggers recurring scheduling. Only the API is published to the developer host. API, worker, and beat share one application image but run as separate processes.

**Tech Stack:** Python 3.12+, FastAPI, SQLAlchemy 2.x, Alembic, Pydantic 2.x, PostgreSQL, Redis, Celery 5.x, httpx, Pytest, Ruff, Docker Desktop / Docker Compose, GitHub Actions.

**Spec:** `docs/design.md`

## Global Constraints

- v0.1 runs locally on Docker Desktop on macOS.
- Application endpoints are versioned under `/api/v1` except `/healthz`, `/readyz`, and FastAPI `/docs`.
- PostgreSQL is the durable source of truth; Redis contains no irreplaceable state.
- Only the API publishes a host port by default: `localhost:8000`.
- PostgreSQL and Redis remain private to the Compose network.
- Expected network/probe failures are persisted as check results and do not crash the worker.
- Application processes log to stdout/stderr, not application-managed log files.
- No real credentials are committed. `.env` is ignored; `.env.example` is committed.
- Custom containers run as a non-root application user where practical.
- v0.1 does not add a custom frontend, authentication, alert delivery, Prometheus/Grafana/Loki, Podman, Ansible, OpenTofu, Kubernetes, or production secrets management.
