# Ops Appliance v0.2 Linux Appliance Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Convert the existing Ops Appliance into a reproducible single-node Ubuntu appliance deployed by Ansible and supervised as independent rootless Podman/Quadlet services, with versioned multi-architecture release images published to GHCR.

**Architecture:** Preserve the v0.1 API/PostgreSQL/Redis/Worker/Beat process boundaries, but replace Docker Compose as the production-style supervisor with an Ubuntu 26.04 LTS host, a dedicated `opsappliance` account, rootless Podman, systemd user services generated from administrator-managed Quadlets, UFW, and Ansible. GitHub Actions builds the application image once for ARM64 and AMD64; Ansible selects an explicit image tag, pulls it, runs migrations during deployment, starts/restarts services, and fails if `/readyz` never succeeds.

**Tech Stack:** Ubuntu 26.04 LTS ARM64, UTM Shared Network, Ansible Core 2.21, ansible-lint 26.x, community.general 13.x, Podman 5.7, systemd/Quadlet, UFW, GitHub Actions, GitHub Container Registry, Docker Buildx/QEMU, FastAPI, Celery, PostgreSQL 16.15, Redis 7.4.11.

**Spec:** `docs/superpowers/specs/2026-09-14-v0.2-linux-appliance-design.md`

## Global Constraints

- Initial appliance host: Ubuntu 26.04 LTS ARM64 in UTM on Apple Silicon.
- UTM networking: Shared Network mode for v0.2.
- Base VM creation and Ubuntu installation remain manual; automation begins after SSH works.
- Ansible owns host configuration after bootstrap.
- Runtime account: dedicated `opsappliance` user with UID `1100`, locked password, home directory, and no sudo privileges.
- Podman workload execution is rootless; Ansible may use `become: true` for host administration.
- Administrator-managed rootless Quadlets live under `/etc/containers/systemd/users/1100/`.
- `loginctl enable-linger opsappliance` is required so the user service manager exists after reboot without login.
- Appliance services remain independent containers: API, Worker, Beat, PostgreSQL, Redis.
- Shared Podman network name: `ops-appliance`.
- PostgreSQL volume name: `ops-postgres-data`.
- Only API TCP/8000 is host-published; PostgreSQL and Redis must have no host port mappings.
- UFW policy: deny incoming by default, allow outgoing, allow OpenSSH, allow TCP/8000.
- PostgreSQL image remains `docker.io/library/postgres:16.15-bookworm` for v0.2 unless compatibility testing proves it unusable.
- Redis image remains `docker.io/library/redis:7.4.11-alpine` for v0.2 unless compatibility testing proves it unusable.
- Application image: `ghcr.io/robotonist/ops-appliance:<explicit-tag>`.
- Application deployment must never use `latest`.
- Release image platforms: `linux/amd64,linux/arm64`.
- Redis remains intentionally ephemeral; PostgreSQL state must survive container restart and full VM reboot.
- Alembic migrations run during Ansible deployment, not as a normal boot-time service.
- A deployment succeeds only after `http://<appliance-host>:8000/readyz` returns successfully within a bounded retry window.
- Real secrets are never committed. Local inventory and local secret vars are Git-ignored; committed `.example` files document required inputs.
- Existing Docker Compose development and CI smoke paths remain valid throughout v0.2.
- Kubernetes, reverse proxy/TLS, authentication, centralized observability, automated rollback, backup/restore, digest pinning, SBOMs, and signing remain out of scope.

- Produces: public-capable `ghcr.io/robotonist/ops-appliance:<tag>` manifests containing both `linux/amd64` and `linux/arm64` images. Manual dispatch supports pre-release appliance testing; Git tags support formal releases.

- [ ] **Step 1: Add the OCI source label to the runtime image definition**


- [ ] **Step 2: Create the image publishing workflow**

Create `.github/workflows/image.yml`:

```yaml
name: Publish Image

"on":
  push:
    tags:
      - "v*.*.*"
  workflow_dispatch:
    inputs:
      image_tag:
        description: "Explicit image tag for pre-release testing (for example v0.2.0-rc1)"
        required: true
        type: string

permissions:
  contents: read
  packages: write

env:
  IMAGE: ghcr.io/robotonist/ops-appliance

jobs:
  publish:
    runs-on: ubuntu-latest
    timeout-minutes: 30

    steps:
      - name: Check out repository
        uses: actions/checkout@v7

      - name: Select explicit image tag
        id: tag
        shell: bash
        run: |
          if [[ "${GITHUB_REF_TYPE}" == "tag" ]]; then
            echo "value=${GITHUB_REF_NAME}" >> "$GITHUB_OUTPUT"
          else
            echo "value=${{ inputs.image_tag }}" >> "$GITHUB_OUTPUT"
          fi

      - name: Reject latest tag
```

## Implementation Notes

### Why UFW

Ubuntu documents UFW as its default firewall frontend, and Ubuntu 26.04 ships the package. v0.2 only needs a host firewall with a simple default-deny policy and two explicit inbound allowances, so direct nftables management would add complexity without improving the project requirement.

### Why administrator-managed rootless Quadlets

Podman supports rootless Quadlet search paths under `/etc/containers/systemd/users/${UID}`. This allows root/Ansible to own deployment definitions while generated units run in the unprivileged user's systemd manager. Do not replace this with `User=opsappliance` inside rootful system units; that is a different security model.

### Why pre-pull the application image

Quadlet/systemd may otherwise spend service startup time pulling images. Ansible already knows the requested release and is the deployment orchestrator, so image transfer belongs in the deployment phase. It also makes an unavailable/mistyped release tag fail before services are restarted.

### Why no `systemctl enable` for generated Quadlet services

Quadlet services are generated units. The `.container` files carry `[Install]` relationships such as `WantedBy=default.target`; after generator reload, those relationships establish boot behavior. The implementation should reload/start generated units, not treat generated service files as hand-authored units to enable conventionally.

### Why `v0.2.0-rc1` during implementation

The final `v0.2.0` image should correspond to the merge commit on stable `main`. The feature branch still needs a deployable image for real UTM testing, so a manually dispatched explicit pre-release tag provides that artifact without using `latest` or merging unfinished work.
