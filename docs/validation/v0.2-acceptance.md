# Ops Appliance v0.2 Acceptance

## Test Information

* **Test date:** 2026-09-20
* **Appliance OS:** Ubuntu 26.04.1 LTS
* **Architecture:** aarch64
* **Deployment platform:** UTM on Apple Silicon
* **Application image:** `ghcr.io/robotonist/ops-appliance:v0.2.0-rc1`
* **Runtime model:** Rootless Podman containers managed by systemd user services generated from Quadlet definitions

## Acceptance Summary

The v0.2 Linux appliance successfully demonstrated repeatable Ansible deployment, independent application processes, persistent PostgreSQL state, rootless service recovery after a full VM reboot, and automatic resumption of recurring monitoring.

## 1. Repeatable Ansible Deployment

The same deployment was executed twice consecutively using the explicit pre-release image:

```bash
ansible-playbook -K \
  -i ansible/inventory/local.ini \
  ansible/deploy.yml \
  -e ops_appliance_version=v0.2.0-rc1
```

Both runs completed successfully with:

```text
ok=37
changed=2
unreachable=0
failed=0
```

The two expected changed tasks were:

* deployment-time Alembic migration execution
* intentional restart of the application services

Existing users, firewall rules, Podman network, persistent volume, Quadlet definitions, and host configuration converged without duplication.

**Result:** PASS

## 2. Recurring Monitoring Pipeline

A deterministic self-monitoring target was created through the appliance API.

* **Target name:** `appliance-self-health`
* **Target UUID:** `2100f145-a71c-46c2-a4ab-dd00dc5941bc`
* **URL:** `http://ops-api:8000/healthz`
* **Interval:** 10 seconds
* **Expected status:** HTTP 200

Multiple healthy results were recorded approximately every 10 seconds.

This exercised the complete application path:

```text
Celery Beat
    ↓
Redis broker
    ↓
Celery Worker
    ↓
HTTP probe of ops-api
    ↓
PostgreSQL result persistence
```

**Result:** PASS

## 3. Worker Process Isolation

`ops-worker.service` was intentionally stopped while the API and Beat services remained running.

Observed service state:

```text
ops-api.service      active
ops-worker.service   inactive
ops-beat.service     active
```

While the Worker was stopped:

```text
GET /healthz
{"status":"ok"}

GET /readyz
{"status":"ready","database":"ok","redis":"ok"}
```

The API remained available and its PostgreSQL and Redis dependencies remained healthy.

The Worker was then restarted and returned to `active`.

**Result:** PASS

## 4. Pre-Reboot Durable State

Before reboot, the monitoring target had:

```text
91 persisted check results
```

The target and its history were stored in PostgreSQL using the persistent Podman volume.

## 5. Full VM Reboot Recovery

The Ubuntu appliance was rebooted using:

```bash
sudo.ws systemctl reboot
```

No containers or application services were manually started during recovery.

SSH became reachable again automatically.

The API `/readyz` endpoint subsequently returned successfully without operator intervention.

The rootless systemd user manager automatically restored the appliance services from the administrator-managed Quadlet definitions.

The following services were confirmed active after reboot:

```text
ops-postgres.service
ops-redis.service
ops-api.service
ops-worker.service
ops-beat.service
```

**Result:** PASS

## 6. PostgreSQL Persistence

Before reboot:

```text
91 check results
```

After reboot:

```text
114 check results
```

The original monitoring target remained available using the same UUID after the reboot.

Because the post-reboot history count remained greater than the pre-reboot count, the PostgreSQL-backed target and historical results survived the full VM reboot.

**Result:** PASS
